# Mnemosyne v0.3 设计:跨 Agent 自动记忆形成 + LongMemEval 基准

- 状态:Draft
- 日期:2026-06-16
- 范围:两个独立特性,合并为一个 v0.3 里程碑
  - **T1** — 跨 Claude Code / Codex / Hermes 的自动记忆形成(auto memory formation)
  - **T2** — LongMemEval 检索基准 adapter,产出可对标的 recall 数字

---

## 0. 背景与动机

Mnemosyne v0.2.1 在检索栈(BM25 + 可选向量 + RRF 融合 + cross-encoder rerank)、
关系图谱、生命周期、MCP、三方集成上已较完整。参考同类项目(mem0、cognee、Memori、
MemoryOS、MemPalace 等)后,识别出两个结构性差距:

1. **写入是纯手动的**:记忆靠 agent 自觉调 `write`,或 Codex 恰好吐 `**新发现:**` 块。
   agent 一旦忘记,记忆就丢。mem0 类产品的核心卖点正是 `add(messages)` 自动抽取。
   这是 Mnemosyne 与同类之间唯一的体验代差。
2. **检索质量无法对外证明**:`eval run` 只在内部 50 条语料上算 recall/MRR,
   只能证明"未退化",证明不了"够好"。同类普遍报 LongMemEval 数字。

设计约束(不可违背的项目调性):

- 基础安装零重依赖(当前仅 `portalocker`);LLM/向量能力一律 optional extra。
- 文件即接口:记忆始终是 Markdown + YAML frontmatter,可 grep、可审计、可手改。
- 热路径无强制 LLM 调用。
- 跨 agent:任何能力都不能只为 Claude Code 服务。

## T1 — 跨 Agent 自动记忆形成

### 决策记录

| 议题 | 决定 | 被否方案及劣势 |
|---|---|---|
| 自动化程度 | **全自动直接写入**(mem0 式),不经人工确认队列 | 候选队列体验不如 mem0;低强度兜底仍会让噪音在被淘汰前参与注入 |
| 抽取引擎 | **可插拔:启发式默认 + LLM 可选** | 纯 host-model(Stop block-continue)仅 Claude Code 生效,违反跨 agent 约束 |
| 去重护栏 | **纳入 v0.3** | 全自动 + 无去重 = store 快速变脏 |

### 核心原则:抽取核心与触发时机解耦

三个 agent 接入面不同,但都汇聚到同一个抽取核心 + 落盘路径。"谁来触发"是薄适配层,
"抽取什么 / 怎么写"是共享核心。

```
┌─────────────┐   ┌──────────┐   ┌──────────┐
│ Claude Stop │   │  Codex   │   │  Hermes  │   ← 触发器(薄适配层)
│    hook     │   │  ingest  │   │  plugin  │
└──────┬──────┘   └────┬─────┘   └────┬─────┘
       └───────────────┼──────────────┘
                       ▼
            ┌──────────────────────┐
            │  mnemosyne distill   │   ← 统一 CLI 入口
            └──────────┬───────────┘
                       ▼
            ┌──────────────────────┐
            │   distill.py 核心     │
            │  engine(可插拔)      │   heuristic | llm | host-emitted
            │  → list[Finding]     │
            └──────────┬───────────┘
                       ▼
            ┌──────────────────────┐
            │  去重护栏(BM25+向量)  │   命中近似 → skip 或 supersedes
            └──────────┬───────────┘
                       ▼
            ┌──────────────────────┐
            │  write_finding()      │   复用 codex.py 现成落盘
            │  (Markdown + index)   │
            └──────────────────────┘
```

### 组件 1 — 抽取核心 `mnemosyne/distill.py`

职责:把一段对话文本转成 `Finding` 列表。**复用** `codex.py` 的 `Finding` /
`write_finding` / `update_memory_index`,不重造落盘。

公开接口:

```python
def distill(
    transcript_text: str,
    *,
    engine: Extractor | None = None,   # None → 按 config 选默认
    config: dict | None = None,
) -> list[Finding]: ...
```

引擎抽象(照搬 `embedding/base.py` 的 optional-backend 模式):

```python
class Extractor(Protocol):
    def extract(self, transcript_text: str) -> list[Finding]: ...
```

- **`HeuristicExtractor`(默认,纯 stdlib)**:基于规则从 transcript 抓信号:
  - 报错栈/失败输出 紧跟 修复 edit → `pitfall`
  - "用 X 不要 Y" / "下次……" / 用户纠正措辞 → `preference`
  - 多次工具调用才搞清的模块职责 → `codebase`
  - "选 A 不选 B 因为……" → `arch_decision`
  - 每条候选带 `confidence`,低于阈值丢弃。精度有限,但零依赖、确定性、可在三 agent 上跑。
- **`LLMExtractor`(可选 `[distill]` extra)**:OpenAI 兼容 API 或本地 ONNX,
  用固定的抽取 prompt 产出结构化 finding。质量贴近 mem0。默认关闭。
- **`HostEmittedExtractor`**:不真正"抽取",只对 agent 已经吐出的 `**新发现:**`
  块跑 `parse_findings`。用于 agent 自身就是 LLM、能自蒸馏的场景(见触发器)。

引擎选择由 config 决定:

```toml
[distill]
enabled = false           # v0.3 默认关,显式开启
engine = "heuristic"      # heuristic | llm | host
confidence_threshold = 0.6
max_findings_per_session = 5
[distill.llm]
backend = "openai"        # openai | onnx
model = "..."
```

### 组件 2 — 统一 CLI `mnemosyne distill`

```
mnemosyne distill [--transcript PATH | --stdin] [--dry-run] [--source NAME] [--scope ...]
```

- 读 transcript(Claude Code JSONL transcript / 纯文本)→ 调 `distill()` →
  过去重护栏 → `--dry-run` 时打印将写入的 finding,否则自动写入。
- 三个 agent 的触发器最终都收敛到这一条命令(或其 Python 等价调用)。

### 组件 3 — 各 Agent 触发器(薄适配)

| Agent | 触发 | 实现 |
|---|---|---|
| **Claude Code** | 增强 `hooks/stop.py` | 当前 `json.load(sys.stdin)` 丢弃了输入;改为读取 `transcript_path`,在已有 maintain/core-candidate 逻辑后追加:若 `distill.enabled` 则调 `distill()` 写入。用 `stop_hook_active` 防重入。Stop 是冷路径,延迟无所谓。 |
| **Codex** | 现有 `codex-ingest` + 强化 AGENTS.md | `templates/AGENTS.md` 已约定吐 `**新发现:**`;保持不变,`codex-ingest --commit` 即自动写。可选:提供 wrapper 在 Codex 会话末自动跑 ingest。 |
| **Hermes** | MemoryProvider 插件加 session-end 钩子 | 在 `integrations/hermes/` 插件中,会话结束时对对话缓冲调 `distill()`,`--source hermes`。 |

> 说明:Claude Code 触发器内部用 config 选定的 engine(默认 heuristic);
> Codex/Hermes 因 agent 本身是 LLM,天然走 host-emitted 路径(它们自己产出 finding)。
> 三方落盘、去重、格式完全一致。

### 组件 4 — 去重 / 冲突护栏

写入任何 finding 前,核心在目标 store 内查近邻:

1. 用现有 BM25(及 `embedding.enabled` 时的向量近邻)对 finding 的 title+content 检索 top-k。
2. 相似度 ≥ `dedup_threshold`:
   - **近重复** → 跳过写入,改为给已有记忆 `+bonus_recall` 并刷新 `last_accessed`。
   - **矛盾**(同主题、结论相反的启发式信号) → 写入新记忆,并自动建 `supersedes` 链接
     指向旧记忆(触发现有 `demote_target` 降权)。

```toml
[distill]
dedup_threshold = 0.85
```

这既防全自动污染,也是 Tier 3(自动冲突检测)的第一步。

### 错误处理

- 抽取核心任何异常都不得让 Stop hook 失败:沿用现有 `hook_safe()`,exit 0。
- `LLMExtractor` 不可用(无 key / 网络失败)→ 记 warning,回退 heuristic 或跳过,绝不崩。
- transcript 解析失败 → 跳过抽取,maintain/core-candidate 逻辑照常。

### 测试

- `tests/test_distill.py`:
  - `HeuristicExtractor` 对固定 transcript fixture 产出预期 finding(报错+修复、偏好、决策)。
  - 去重护栏:写入已存在的近似记忆 → 跳过 + 刷新强度;矛盾 → 建 `supersedes`。
  - `distill --dry-run` 不落盘。
- `tests/test_hooks.py` 扩展:Stop hook 在 `distill.enabled=true` 时调用核心;
  `stop_hook_active=true` 时不重入;`distill.enabled=false` 时行为与 v0.2.1 完全一致。

## T2 — LongMemEval 检索基准 adapter

### 决策记录

| 议题 | 决定 | 被否方案及劣势 |
|---|---|---|
| 先做哪个 | **LongMemEval** | MemoryAgentBench 排后续;LongMemEval 是 mem0/MemPalace 共同对标项 |
| 数据分发 | **按需下载 + 内置 5 条 sample** | 全量塞 repo 体积爆炸 |
| 评测协议 | **per-instance 隔离 haystack** | pooled 单 store 与官方数字不可比 |
| 指标 | recall@{1,5,10} + MRR,**按问题类型拆分** | 只报总分掩盖弱项 |
| 检索管线 | 支持**完整混合栈**;BM25-only 留 CI 快档 | 仅 BM25 严重低估真实能力 |
| 端到端 QA | **不做**(future) | 需 LLM judge,偏离轻量路线 |

### 现状约束

`eval/__init__.py` 的 `run_evaluation` 当前:① 只构建内存 `BM25`,绕开 FTS5 +
向量 + RRF + rerank;② 用**单个共享** `seed_memories.jsonl` 对所有 query。
LongMemEval 是 per-instance(每问题自带 haystack + 干扰 session),且要对标数字
必须能走完整管线。因此 T2 = adapter + harness 扩展两部分。

### 组件 1 — adapter `mnemosyne/eval/adapters/longmemeval.py`

把 LongMemEval 原始数据转成既有 corpus 格式 + 实例分组:

```python
def convert(raw_path: Path, out_dir: Path, *, max_instances: int | None = None) -> None:
    """raw LongMemEval json → seed_memories.jsonl + corpus.jsonl(带 instance_id 分组)"""
```

映射:

- 每个 haystack session → 一条 seed 文档,`id = "lme-<instance>-<session_idx>"`,
  `text = session 拼接文本`,新增字段 `instance_id`、`session_date`(供时序题)。
- 每个 instance 的 `answer_session_ids` → `EvalItem.expected_ids`。
- `EvalItem` 扩展两个可选字段:`instance_id`(隔离用)、`question_type`(拆分用)。

`corpus.py` 的 `EvalItem` 增补:

```python
@dataclass
class EvalItem:
    query: str
    expected_ids: list[str]
    paraphrase_of: str = ""
    notes: str = ""
    instance_id: str = ""        # 新增:per-instance 隔离
    question_type: str = ""      # 新增:按类型拆分指标
```

(均带默认值,向后兼容现有 corpus。)

### 组件 2 — harness 扩展 `run_evaluation`

- **per-instance 隔离**:`instance_id` 非空时,按 instance 分组 seed 文档,
  每个 instance 构建独立检索引擎,只用该 instance 的文档回答其 query。
- **可选完整管线**:新增 `pipeline` 参数:
  - `"bm25"`(默认,现状,CI 快档)
  - `"full"`:走真实 `SearchEngine`(FTS5+向量+RRF+rerank),把 instance 文档灌入临时 store。
- **多 k 值 + 类型拆分**:recall@1/5/10、MRR;按 `question_type` 分组聚合并打印矩阵。

### 组件 3 — 数据获取 `mnemosyne eval fetch`

```
mnemosyne eval fetch longmemeval [--variant s|m] [--dest DIR]
```

下载官方数据到本地缓存(不入 repo);打印许可与来源。仓库内置
`eval/fixtures/longmemeval_sample.json`(5 条)供单测与 CI。

### CLI 变更

```
mnemosyne eval run   [--corpus FILE] [--pipeline bm25|full] [--by-type]
mnemosyne eval fetch longmemeval [--variant s|m]
mnemosyne eval convert longmemeval --raw PATH --out DIR
```

`eval run` 现有无参行为保持不变(默认 corpus + bm25 + legacy/bigram 对比)。

### 测试

- `tests/test_eval_longmemeval.py`:
  - `convert()` 对内置 5 条 sample 产出正确的 seed + corpus,`expected_ids` 映射正确。
  - per-instance 隔离:instance A 的 query 不会命中 instance B 的文档。
  - `--by-type` 输出含各问题类型的 recall。
  - `pipeline="full"` 路径在装了向量 extra 时可跑(无则 skip)。
- 现有 `tests/test_eval.py` 保持通过(向后兼容)。

## 里程碑拆分(供后续 implementation plan)

1. **T1-a** 抽取核心 + heuristic 引擎 + `distill` CLI(`--dry-run`)
2. **T1-b** 去重 / 冲突护栏
3. **T1-c** Claude Code Stop hook 触发器
4. **T1-d** Codex / Hermes 触发器接线 + LLM 引擎(可选 extra)
5. **T2-a** `EvalItem` 扩展 + adapter `convert()` + 内置 sample
6. **T2-b** harness per-instance 隔离 + 多 k + 类型拆分
7. **T2-c** `eval fetch` 下载器 + 完整管线 `pipeline="full"`

每个里程碑独立可测、独立可合并。

## 明确不做(v0.3 范围外)

- 候选确认队列 / `mnemosyne review` UX(已选全自动)
- 端到端 QA 准确率评测(需 LLM judge)
- MemoryAgentBench adapter(排后续里程碑)
- 遗忘曲线 / 时序知识图谱(Tier 3,排 v0.4)

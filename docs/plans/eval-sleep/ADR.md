# Bounded sleep output continuation

Input batches remain version 1. `cursor`/`next_cursor` describe the exported input range only. Optional `blocked` entries name invalid records by inventory position and filename, never copy their contents. The 10,000-entry inventory hard limit remains; only page bodies (at most 100 records / 4 MiB) are read. Oversized or malformed records are reported, not truncated. Unsafe links fail closed.

`sleep import` and MCP `sleep_import` accept the existing `{batch, proposals}` object or `{batch, proposals, output: {index, total}}`. Index is zero-based; total is declared on page zero, immutable, and limited to 1,000. Each request retains the 20-proposal / 64 KiB output budget. Old callers submit one output page. The run ID hashes the complete batch, the receipt ID hashes run ID and output index; each receipt binds the complete request hash. Different content at an existing index conflicts. Pages must arrive in order; identical retries return the saved receipt.

One store lock covers current input validation, proposal planning, and committing each output page. Pending proposals, the receipt, run manifest, and (only on the final page) input progress use the existing MutationPlan journal. No separate transaction engine or automatic proposal approval is introduced. Reports are bounded metadata pages; consumers retain or read each receipt, rather than concatenate a potentially unbounded response. `next_output` is independent of `next_cursor`; cursor status remains partial when blocked records were encountered in the current snapshot.

The inventory snapshot intentionally includes file metadata (including ctime on Unix), so access-metadata rewrites also invalidate cursors. Restart export at zero after any such change. Semantic revision/hash validation remains required. A stale new result is never applied to a changed source. An exact committed v2 receipt is returned before current-source validation; it binds the store ID and does not reapply any effect. Replay of an older completed batch cannot rewind a later input cursor. External edits to a journal target retain the journal and fail recovery.

The exported inventory is bounded but fully enumerated; arbitrary-size stores are not supported. A 10,001-entry store fails explicitly. This is a documented hard ceiling, not unlimited-store acceptance. All testing uses isolated synthetic stores.

Input commits are sequential: exporting ahead is allowed, importing ahead is rejected. A partial output run reserves the current input cursor (`active_run`); only that run can finish that range. Restart at input zero after a snapshot change abandons the stale reservation. Identical already-committed page retries remain valid and cannot rewind progress. Legacy v1 report replay preserves its bytes and repairs an interrupted legacy cursor write.

Export also bounds serialized input metadata to 48 KiB, leaving receipt overhead below 64 KiB even for long IDs and unresolved links. Output reports remain metadata only. To resume after interruption, resend the last exact import request; its receipt reports `next_output`. To process another input page, use `sleep cursor` only once `input_committed` is true. A completed output run may still have `status: partial` because more inputs or blocked records remain. Fix blocked source records and restart export at zero before claiming the store is completely reviewed.

Completed v2 sleep receipts are included in portable snapshots. Snapshot creation and restore refuse unfinished current continuations because their inventory is bound to filesystem metadata. Restored completed receipts support exact retries, while new scans must start at zero. Forking a snapshot containing sleep records is explicitly unsupported; it must not reuse source-store receipt identity. Old readers reject the new snapshot entries. Mixed-writer recovery of the new sleep journal targets is not certified; no old-writer compatibility claim is made.
